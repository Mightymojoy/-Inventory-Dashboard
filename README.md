# ITO 库存看板 (Inventory Dashboard)

ITO 品牌电商库存日常管理看板。每日更新「库存-每日.xlsx」→ 一键刷新 → 双击打开成品看板。

## 文件说明

| 文件 | 说明 |
|------|------|
| `ITO库存看板.html` | **自包含成品**（数据内嵌，双击即开，无需服务器） |
| `build_inventory.py` | 构建脚本：读 Excel → 算指标 → 生成看板 |
| `inventory_dashboard.html` | 看板模板（不含数据，供构建脚本嵌入数据） |
| `inventory_data.json` | 最近一次构建的数据快照 |
| `stockout_history.json` | 缺货档案（一 SKU 一条汇总，含「历次事件」数组） |
| `stockout_events.json` | **缺货事件台账**（一 SKU 多事件，每次缺货一行，唯一事实源） |
| `刷新库存看板.bat` | 每日一键刷新脚本（双击即可） |

## 使用方式

1. 将每日 ERP 导出的库存表命名为 `库存-每日.xlsx` 放入本目录（数据源含业务数据，已通过 .gitignore 排除，不上传）
2. 双击 `刷新库存看板.bat`（自动探测 Python 环境并运行构建）
3. 构建完成后自动打开 `ITO库存看板.html`

手动刷新：
```
py build_inventory.py
```

## 看板模块

- 总览（KPI：在售 SKU / 可发库存 / 货值 / 缺货 / 预警 / 停采 / 未上市 / 在途 / 到货）
- 库存健康度（缺货 / 急需关注 / 缺货风险 / 安全 / 滞销 五级分布）
- 缺货 & 预警清单（生命周期 + 状态 + 分类 + 搜索 四重筛选）
- 滞销清单（货值汇总 KPI）
- 到货监控（依赖「供应链提货计划表」，有则按日期日历、无则展示在途）
- 分类维度（品类 / 系列 / 状态 / 搜索 四重筛选）
- 商品 SKU 总览（全量正品目录，含生命周期筛选）
- 旅行配件 & 赠品总览
- 缺货明细记录（**当前在缺 / 历史记录** 两段切换，默认只看在缺；含商品编码、生命周期、「已停采 / 已下市」状态）

## 生命周期（2026-10-27 新增）

`level`（库存健康度）与 `lifecycle`（商品生命周期）是**两个正交维度**：

| lifecycle | 含义 | 是否计入缺货 |
|---|---|---|
| 在售 | 正常在卖 | ✅ 计入（缺货/预警只由在售产生） |
| 停采 | 已停止采购，不会补货 | ❌ 不计入 |
| 未上市 | ERP 已建档、尚未上架（可发恒 0）；含**首批货未到仓** | ❌ 不计入 |
| 定制 | 按需定制，可发=0 属正常 | ❌ 不计入 |

判定优先级（不可调换）：
**未上市 > 定制 > 分类停采 > 限定色停采 > 旧版淘汰 > 指定色停采 > 在售**

1. 货品名称含 `FIND ITO`，或命中 `UPCOMING_EXTRA`（名称片段）/ `UPCOMING_CODES`（商品编码）→ 未上市
1.5 **首批货未到仓闸门**（2026-10-29 新增，见下节）→ 未上市
2. 分类属定制类（定制旅行箱 / 定制包袋 / 套装）→ 定制
3. 分类以「停采」开头 → 停采

### 首批货未到仓 ≠ 缺货（2026-10-29 新增闸门）

新品在 ERP 已建 SKU、首批货还没到仓时，可发为 0/负、名称也不带 `FIND ITO`，
旧口径会误判成「在售 · 缺货」并每天续记缺货天数。PISTACHIO 2 STRIPED
柔雾棕/琥珀粉/月光紫 × 20/26/30 共 9 个 SKU 就这样凭空记了 5~17 天/个
（2026-08-25 → 09-04~09-11，而该系列 09-15 才上市）。

`apply_prelaunch_gate()` 在汇总指标之前改判，四条全中才判（宁可漏判不可误判）：

1. `level == 缺货`（在售 且 可发 ≤ 0）
2. 该 SKU 在 `入库明细同步.xlsx` 全部批次中**从未出现过**（从没到过货）
3. 同系列至少 1 个**其他** SKU 出现过（系列有正常到货流程）—— 防误伤的关键：
   LUGGAGE TAG / COSMETIC BAG 这类本来就不进入库明细的品类，系列内兄弟也全无记录
4. 在途量 = 0（有在途属正常补货等待）

配套保护：入库明细最新批次距今 > `ARRIVAL_GATE_STALE_DAYS`（7 天）时闸门自动停用并告警，
避免拿陈旧数据误判。改判会**同步 `catalog`**，防止「总览说在售、缺货里没有、未上市也不含」。
回归测试见 `_test_prelaunch_gate.py`（4 个场景：命中 / 不误伤 / 品类豁免 / 过期停用）。
4. 命中 `LIMITED_COLOR_DISC` → 停采（年度限定色：行李箱 9 + 旅行生活 30）
5. 命中 `SUPERSEDED_DISC` → 停采（旧版被新版替代，ERP 漏标分类的尾货）
6. 命中 `COLOR_PHASE_OUT` → 停采（指定颜色退出，如 CAMIRA ERA 黛蓝/稻黄）
7. 其余 → 在售

> **停采 / 在售以 ERP「分类」字段为主依据，不做名称推断**（2026-10-27 老大确认）。
> ERP 已经把停采商品单独归入「停采旅行箱」「停采包袋」分类，直接采信即可；
> 少数漏标的旧版尾货，用商品编码名单补（第 4、5 级），**名单一律按编码，不用名称关键字**。
>
> **为什么绝不能用「名称含 2026版 / TRUNK」推断新旧版**：
> 名称是前缀关系 —— `亮面炭黑20英寸旅行箱` 是 `亮面炭黑20英寸旅行箱 2026版` 的前缀，
> 包含匹配会把在售的新版一并打成停采，实测会误伤 6 个「2026版」（可发合计 534 件），
> 同系列「FIND ITO」（未上市）与带客户名的定制款也会被误判。

### 人工名单（ERP 未标注，只能靠人工维护）

这三张名单存在的唯一原因：**ERP 字段没有对应信息**。一旦 ERP 能直接标注，应改为读字段。

| 常量 | 键 | 用途 | 当前收录 |
|---|---|---|---|
| `UPCOMING_EXTRA` | 名称片段 | ERP 分类在售、名称无 `FIND ITO`，但未上市 | 1 个（MYCENA 芽绿 16L） |
| `UPCOMING_CODES` | **商品编码** | 同上，第二批起统一用编码 | 11 个（PACKING CUBE ×9、VANITY ×2） |
| `LIMITED_COLOR_DISC` | **商品编码** | 年度限定色，售完即止 → 停采 | 39 个（行李箱 9 + 旅行生活 30） |
| `SUPERSEDED_DISC` | **商品编码** | 旧版被 2026版/TRUNK 替代，ERP 仍标「旅行箱」 | 2 个（PISTACHIO STRIPED 亮面炭黑/烟白 28 英寸） |
| `COLOR_PHASE_OUT` | **商品编码** | 指定颜色退出（非新旧版迭代） | 4 个（TRUFFLE BACKPACK 2 CAMIRA ERA 黛蓝/稻黄 × 12L/18L） |

**为什么限定色用编码而不是色名关键字**（重要，别再犯）：

气泡粉 / 波子绿 / 苏打橙 三个色名全库命中 **45 个 SKU**，按品类三分：

| ERP 分类 | SKU 数 | 可发 | 处置 |
|---|---|---|---|
| 旅行箱 | 9 | 351 件 | 限定色 → **停采** |
| 旅行生活 | 30 | 4,717 件 | 限定色周边 → **停采**（伞/水杯/购物袋/洗漱包/行李牌/手机包/电脑内胆包） |
| 包袋 | 6 | 646 件 | 正常在售，**保留不动**（2026-10-27 老大明确选定） |

写成 `if '气泡粉' in name: 停采` 会把**包袋 646 件**正常在售库存一并打成停采
（若连旅行箱一起算，误伤面更大），KPI 出现剧烈但虚假的改善。
所以**按商品编码精确锁定**。

**维护约定**：
- `UPCOMING_*` 中的商品**上市后必须删除条目**，否则会一直显示「未上市」
- 限定色**明年若以新年度限定色回归，是新的商品编码**，不会被旧名单误伤
- 但**新增尺寸不会自动纳入**，需手工补编码

## 停采 SKU 的统计口径

停采 SKU 的来源已分两类：

1. **ERP 停采分类**（停采旅行箱 / 停采包袋）——**不进在售池** `skus`
2. **人工名单**（`LIMITED_COLOR_DISC` / `SUPERSEDED_DISC` / `COLOR_PHASE_OUT`）
   ——ERP 分类仍是「旅行箱 / 旅行生活 / 包袋」，**仍在池内**，只是 lifecycle 被判停采
   （当前池内停采 45 个 = 限定色 39 + 旧版 2 + 指定色 4，可发合计 5,736 件）

因此：

- 「缺货 & 预警清单」的**停采筛选在售视图下必然为空**（页面会给出解释并引导到商品总览）
- KPI「停采 SKU」用**全量目录 `catalog`** 统计（当前 830 个，其中 141 个仍有货、可发合计 6,975 件）
- 「商品总览」按生命周期=停采可查看完整清单
- **总可发库存 `total_kf` 含停采尾货**（池内 45 个停采共 5,736 件）：尾货仍在仓、仍可发，货值真实。
  所以 KPI 卡副标题写「含停采尾货」，**不要**再加总「在售 + 定制」去对 32,134
- 判定依据写入 `lifecycle_reason`（在售池与 catalog 都有），可追溯为什么判停采


## 口径说明

- 只看品牌为 ITO 的商品
- 货值按零售价计算
- 健康度阈值：周转 <7 天急需关注、<15 天缺货风险、>90 天滞销（可调整）
- **缺货只统计在售商品**（2026-10-27 起）：停采不会补货、未上市本来没货，二者都不占用「缺货」这个需要行动的口径
- **环图口径闭合**：健康度环图中心 = 在售 SKU 数，与 5 个健康等级分段之和一致；定制作为独立图例单列
- **缺货历史不删除**：停采/未上市的历史挂账标为「已停采」/「已下市」，可追溯但不计入缺货中
- **钉钉推送与页面同源**（2026-10-29 v0.13.9）：`send_dingtalk.py` 不再自己写一套判据，
  缺货 = `level == "缺货"`、急需关注 = `level == "急需关注"`，分类与阈值直接读
  `inventory_data.json` 的 `config`（`stocked` / `urgent_days`）。改口径只改 `build_inventory.py` 一处。
  每日推送会打印口径自检行（钉钉条数 vs 页面 KPI），漂移即告警
